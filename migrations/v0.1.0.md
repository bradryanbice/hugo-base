# Adopting hugo-base in an existing Hugo site

## Why

This is the first release, so there is nothing to upgrade from. This migration
covers the other direction: taking a site that already exists and putting it on
the shared foundation.

It is marked `automatable: false` because two steps need decisions only you can
make: which of the site's own templates are genuinely site specific, and what
the brand's hue and chroma are.

## What changed

Everything the site previously owned by itself (layouts, CSS, head, images,
feeds, CI) now comes from the module, and the site keeps only what is true for
that site alone.

## Steps

Work through these in order. Each one is safe to run twice.

### 1. Take stock before changing anything

```sh
hugo version                    # note it: the base requires 0.166.0 or later
ls layouts layouts/_default layouts/partials 2>/dev/null
grep -rln "static/" content | head
grep -rn "languageCode\|languageDirection\|languageName" config* hugo.toml 2>/dev/null
```

Keep that output. It is the checklist for the rest of this.

### 2. Import the module

```sh
hugo mod init github.com/<owner>/<repo>
hugo mod get github.com/bradryanbice/hugo-base@v0.1.0
```

Add the import to the site's config, in `config/_default/module.toml`:

```toml
[[imports]]
  path = "github.com/bradryanbice/hugo-base"
```

Never run `go mod tidy` in a Hugo site: there is no Go code, so it would drop
the requirement. Use `hugo mod tidy`.

### 3. Delete the layouts the base now provides

This is the step that matters most, and the one that fails silently if skipped.

Hugo still honours the paths it used before v0.146, and it does so **without a
warning**. A site that keeps `layouts/_default/single.html` or
`layouts/partials/` will have those win over the base, so the site looks like
it adopted hugo-base while still rendering its own templates, and none of the
base's accessibility or token work applies. Verified on Hugo 0.166.0.

```sh
ls layouts/_default/ layouts/partials/ 2>/dev/null
```

For each file, decide:

- **The base provides it** (`baseof`, `single`, `list`, `index`/`home`, `404`,
  a head partial, a header, a footer, a nav): delete it. Keep a copy on a
  branch if that feels safer.
- **It is genuinely site specific** (a layout for one content type, a component
  only this site has): move it to a current path.
  `layouts/_default/players.html` becomes `layouts/players/single.html`, and
  `layouts/partials/x.html` becomes `layouts/_partials/x.html`.

When `layouts/_default/` and `layouts/partials/` are empty, remove them.

### 4. Move the site's CSS onto the tokens

Delete the site's own reset, type scale and color variables: the base has them.
What remains is a theme file and, at most, a small amount of site specific CSS.

Create `assets/css/tokens/theme.css` with the brand's inputs. **This needs a
decision**: pick the hue (0 to 360) and chroma (0 is grey, roughly 0.12 to 0.2
is a saturated brand color) that match the site's existing brand.

```css
:root {
  --accent-hue: 250;
  --accent-chroma: 0.14;
  --neutral-chroma: 0.006;
  --font-heading: "Your Font", system-ui, sans-serif;
  --radius-scale: 1;
}
```

Do not copy any file from `assets/css/foundation/`, `assets/css/tokens/scale.css`,
`tokens/color.css`, `tokens/semantic.css`, `main.css` or
`layout/primitives.css`. The lint fails if you do, because overriding those
breaks the design system rather than theming it.

Site specific CSS goes in its own file, linked from an override of
`head/css-site.html`. It is unlayered, so it wins over the base without
`!important`.

### 5. Fix the config keys

```sh
grep -rn "languageCode\|languageDirection\|languageName" config* hugo.toml 2>/dev/null
```

Hugo renamed these in v0.158.0 and the build gate fails on them:

| Old | New |
|---|---|
| `languageCode` | `locale` |
| `languageDirection` | `direction` |
| `languageName` | `label` |

Then add the three opt in files, each one line, so the site inherits the base's
markup, imaging and feed defaults:

```toml
# config/_default/markup.toml
_merge = "deep"
# config/_default/imaging.toml
_merge = "deep"
# config/_default/services.toml
_merge = "deep"
```

And the root keys, which can never come from a module:

```toml
enableRobotsTXT = true
disableHugoGeneratorInject = true
```

### 6. Move images out of static/

```sh
grep -rn "!\[" content | grep -E "static/|^\S+:!\[[^]]*\]\(/" | head
grep -rln "figure" content | head
```

The base's image pipeline resolves page resources and `assets/` only. An image
in `static/` gets no responsive sizes, no WebP and no dimensions, so it causes
layout shift, and the build now **fails** rather than quietly shipping it:

```
image.html: cannot find "/images/chart.png" (page /x). Put it in the page
bundle or under assets/, not in static/.
```

Move each image next to the page that uses it (making the page a bundle:
`index.md` plus the image) or into `assets/`, and reference it by file name.

### 7. Add alt text

Every image needs it. The build fails and names the page, so the error list is
the work list:

```sh
hugo build --gc --minify --panicOnWarning 2>&1 | grep "has no alt text"
```

Write what a reader would miss if the image did not load. Use `alt=""` only for
an image that genuinely adds nothing, which is a decision, not a default.

### 8. Pair noindex with sitemap.disable

Any page carrying `noindex: true` also needs `sitemap.disable: true`. The gate
fails when a noindex page is still listed in the sitemap.

### 9. Take the shared CI, Renovate and managed files

The site gets its CI workflow, pull request template, editorconfig, shared
rules and the `hugo-base.sh` stub from the module. The stub is itself one of
those files, so the first sync runs from the module directory:

```sh
# Where Hugo put the module (it prints one JSON block per module):
hugo config mounts | grep -B2 hugo-base | grep '"dir"'

# Then, with that path:
python3 <module dir>/tools/sync.py --base <module dir> --site .
```

From then on, `./hugo-base.sh sync` is enough, and CI fails if those files fall
behind the version the site pins.

Then point Renovate at the shared preset, in the site's `renovate.json`:

```json
{
  "extends": ["config:recommended", "github>bradryanbice/hugo-base//renovate/hugo"]
}
```

### 10. Pin the toolchain

`mise.toml` and `netlify.toml` must agree on the Hugo and Go versions, and the
drift check fails if they do not.

```toml
# mise.toml
[tools]
"aqua:gohugoio/hugo/hugo-extended" = "0.166.0"
go = "1.27.1"
node = "24.21.0"
```

```toml
# netlify.toml
[build.environment]
  HUGO_VERSION = "0.166.0"
  GO_VERSION = "1.27.1"
  HUGO_CACHEDIR = "/opt/build/cache/hugo_cache/"
```

## Verify

In order. Each one has to pass before the next is meaningful.

```sh
hugo build --gc --minify --panicOnWarning       # no warnings, no deprecations
./hugo-base.sh sync --check                     # managed files current
./hugo-base.sh lint                             # CSS policy and protected paths
./hugo-base.sh quality public                   # axe, contrast, Lighthouse
```

Then confirm the site is actually using the base, rather than its own old
templates:

```sh
grep -c "skip-link" public/index.html           # 1
grep -c "site-header" public/index.html         # 1
```

If those are zero, step 3 is incomplete: the site still has layouts shadowing
the base.

Last, by hand, because no tool covers it: tab through a page, confirm focus is
visible and the skip link comes first, and zoom to 400 percent to check nothing
is clipped.

## If something does not fit

- **A design the theme slot cannot express.** Do not copy a foundation file.
  Open an issue on hugo-base: either the slot is missing something, or the
  design needs revisiting.
- **A template the base should provide.** Same answer. If it would be true for
  every site, it belongs upstream.
- **Task lists in content.** They are off, because Hugo renders them as a
  checkbox with no accessible name. Write the state in words.
- **A site that cannot move an image out of `static/`** (a file referenced by
  an external system, say). Reference it with a plain Markdown link rather than
  an image, or keep a hand written `img` tag and accept that it is exempt from
  the pipeline, documented in the site's own rules file.
