# The CSS policy now covers Sass, and sites may use it

## Why

Two changes that belong together.

The rule used to say no Sass anywhere, including in a consuming site. That was
too strict: a site with years of Sass could not adopt the base at all, even
though the head, the shell, the image pipeline and the checks are worth having
long before the styles are converted. Sites may now write their own styles in
Sass.

The lint only looked at `assets/css/**/*.css`. A site writing Sass was
therefore exempt from the colour and spacing rules without anyone deciding
that. Run against a real site for the first time, the policy found **539
violations** in 3,148 lines of Sass: physical properties, hex colours, raw
lengths. None of it had ever been checked.

So: Sass is allowed, and Sass is checked. Allowing it without checking it would
have made the policy decorative for most of a site's CSS.

## What changed

- `.scss` files under `assets/` are linted, with the same rules as `.css`. Sass
  variables count as variables, so `$space-m` passes the strict value rule and
  a raw `12px` does not.
- A new `.hugo-base-lint-ignore` file exempts paths during a migration.
- The foundation is unchanged: hugo-base itself uses no Sass and never will,
  because its colour system depends on values the browser resolves.

## Steps

1. Run the lint and see where you stand:

   ```sh
   ./hugo-base.sh lint
   ```

   A site with no Sass, or with Sass already following the policy, is done.

2. If it fails and you are not ready to convert, exempt the paths with a reason:

   ```
   # .hugo-base-lint-ignore
   assets/scss/**   # legacy Sass predating hugo-base, conversion tracked in #N
   ```

   Exemptions print on every run. That is the point: an unchecked path should
   stay visible rather than quietly becoming the way things are.

3. If you are ready to fix some of it, the three common findings and what they
   mean:

   | Finding | Fix |
   |---|---|
   | `csstools/use-logical` | `width` becomes `inline-size`, `margin-left` becomes `margin-inline-start`. Right to left languages, and usually clearer. |
   | `color-no-hex` | `#336699` becomes `oklch(...)`. If it is a brand colour, it probably belongs in `tokens/theme.css` as a hue and chroma instead. |
   | `scale-unlimited/declaration-strict-value` | a raw `12px` becomes a spacing token, or a Sass variable if that part has not moved yet. |

4. Decide the direction, and write it down somewhere the next person sees. The
   base's position is that colour should move to tokens first, because contrast
   checking and dark mode depend on it, and that layout and components can stay
   in Sass indefinitely.

## Verify

```sh
./hugo-base.sh lint            # passes, printing any exemptions
hugo build --gc --minify --panicOnWarning
```

## If something does not fit

An exemption with a reason is a legitimate answer, including permanently, for a
site whose styles are not going to be converted. What the base will not do is
pretend the paths are checked when they are not.
